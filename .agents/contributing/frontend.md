# Frontend Architecture

The frontend uses go-app v11 and the repository's Go module, formatter, linter,
and tests. No separate JavaScript dependency pipeline.

## Build And Runtime Boundaries

- `internal/ui/`: go-app components and browser HTTP logic, also testable natively.
- `cmd/frontend/`: browser entry point compiled with `GOOS=js GOARCH=wasm`.
- `cmd/frontend-export/` and `internal/frontendbuild/`: build-time static exporter.
- `bin/web/`: generated HTML, JavaScript, CSS, config, and WebAssembly.
- Backend serves exported files with `net/http`; never import go-app or frontend
  UI packages into backend runtime code.
- Use a standard static file handler such as
  `http.FileServer(http.FS(static))`. All go-app export work happens during build;
  no go-app handler or exporter runs inside the backend process.
- Frontend and backend are separate applications. Their only runtime integration
  is the documented HTTP API, even though they share one Go module.

## API And Configuration

- Use `gen/client/`, generated by oapi-codegen from the OpenAPI contract.
- Never import backend handlers, services, database packages, backend config, or
  server-generated bindings (`gen/api/`) into frontend code. Do not bypass the
  API by calling backend Go functions directly.
- Keep HTTP/data loading separate from component rendering.
- Keep the initial UI simple: call `/listens`, display its response, and handle
  loading, empty results, failures, and retry. Do not implement missing backend
  functionality as part of frontend setup.
- Separate entry points own separate config files:
  - Backend: `cmd/mnemosyne/config/local.yaml` and `docker.yaml`, selected with
    `-config` (default `local`).
  - Frontend exporter: `cmd/frontend-export/config/config.yaml`.
  - Browser: exported `web/config.json`, containing public frontend settings only.
- Never read backend configuration from the frontend or exporter. Configure
  matching API prefixes explicitly in each application.
- Application settings come from config files, never environment variables.
- Compiler target variables (`GOOS`, `GOARCH`) are build-tool settings, not
  application configuration.
- Export only public configuration (`apiPrefix`) to `web/config.json`.
- API prefixes must include leading and trailing slashes. Reject invalid config;
  never silently add missing slashes.
- Never expose backend configuration or credentials in exported browser files.

## Components And Concurrency

- Render methods must work without browser globals or network access.
- Start requests only in browser lifecycle/event handlers.
- Run requests through `app.Context.Async`; apply state changes through
  `app.Context.Dispatch`. Propagate context cancellation.
- Use text nodes for API responses, never raw HTML.

## Quality Gates

- `make fmt`, `make fmt-check`, `make lint`, and `make test` include frontend Go.
- Use the same `.golangci.yaml`, pinned Go toolchain, formatting rules, and test
  conventions for frontend and backend. No separate frontend lint policy.
- Keep root tooling targets working for both applications. Any new tooling or
  CI check must account for frontend and backend, not silently omit either.
- Lint frontend under both native and `js/wasm` targets.
- Test data loading and rendered states natively; compile real WASM in build checks.
- Frontend unit tests use mock HTTP servers or transports, not backend services.
- Use generated OpenAPI Go types and clients, not hand-written copies of the
  contract. Regenerate clients after spec changes and check generation drift in CI.
- Generated clients are checked in; do not edit them manually. Generated static
  output is not checked in.

## Developer Experience And Packaging

- Prefer latest stable, compatible tool versions. Pin Go dependencies in
  `go.mod`/`go.sum` and developer tools in `mise.toml`; keep upgrades straightforward.
- VS Code workspace configuration must support frontend Go with the same linting
  and formatting workflow as backend Go. Remove obsolete TypeScript tooling.
- Keep a simple multi-stage Dockerfile that builds frontend and backend. Runtime
  serves both from one Go server; no Node, Vite, or separate frontend process.
- Maintain Make targets to start and stop the full Docker app. Preserve SQLite
  data across container stops/rebuilds.
- Document build, run, code generation, and quality checks in `docs/frontend.md`.
  Never edit the top-level `README.md`.
- Edit one file at a time; preserve unrelated user changes.
